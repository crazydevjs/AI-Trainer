1. Project Overview

What is AI-Trainer (FORGE)?

FORGE is a web-based AI personal fitness trainer. The user opens their phone or laptop camera, picks an exercise (e.g. squat), and the app watches them through the camera in real time. It detects the body's joints, counts repetitions automatically, scores the quality of each rep, and speaks coaching cues out loud — exactly like a human trainer standing next to you. It also records the workout, tracks weights and personal records, and saves history.

What problem does it solve?

  • Cost & access: Personal trainers are expensive and not always available. FORGE gives 24/7 AI coaching for the price of an app.
  • Bad form → injury: Most people training alone don't know if their form is correct. FORGE detects mistakes (shallow depth, knees caving, rounded back) and corrects them live.
  • Motivation & tracking: It counts reps so you don't have to, tracks progressive overload, detects PRs, and keeps you engaged with voice + a session report.

Why build it?

To combine three things that normally require a coach + a notebook + a video review: (1) real-time technique correction, (2) automatic logging, and (3) progress analytics — all running on the user's own device so it is cheap to operate and private by design.

Target audience

  • Home / gym lifters who train alone and want form feedback.
  • Beginners who don't know correct technique.
  • Intermediate/advanced lifters who want automatic rep + volume + PR tracking.
  • Initial market: India (price-sensitive, mobile-first), then global.

Real-world use cases

  • Doing squats at home with the phone on a tripod — the AI counts and says "go lower".
  • Tracking bench-press weight per set and getting a "new personal record" announcement.
  • Recording a clean set to share on Instagram/WhatsApp with burned-in rep overlay.
  • Reviewing a session report: form 88%, depth 90%, stability 75%, "your depth dropped near the end".

Future roadmap

AI workout recommendations, personalized plans, fatigue/injury-risk detection, LLM-powered conversational coaching, wearable/smartwatch integration, and a native Android app (true gallery save + on-device voice in recordings). See Chapter 23.

2. Overall System Architecture

FORGE is a client-heavy application: the expensive AI computation (pose detection, rep logic, voice) runs in the browser on the user's device. The server only handles auth, saving sessions, and serving data. This is the single most important architectural decision — it gives ~90% gross margins and strong privacy.

Routing

File-based: a folder under src/app = a URL. Two groups:

  • (app)/ — a route group (parentheses = not in the URL). All pages here share the authenticated sidebar layout: dashboard, exercises, workouts, progress, profile, settings, admin.
  • train/[slug]/ — the full-screen trainer, deliberately outside the app shell so there is no sidebar/chrome — only camera + overlays (a hard requirement of the spec). [slug] is a dynamic segment, e.g. /train/barbell-squat.

Route protection lives in src/proxy.ts (Next 16's middleware equivalent): it checks the JWT cookie and redirects unauthenticated users to /login before any protected page renders.

Server vs Client Components

By default Next renders components on the server (fast, secure, no JS shipped). Components that need browser APIs or interactivity opt in with "use client". Example: train/[slug]/page.tsx is a server component that fetches the exercise + history from the DB, then passes them as props to <TrainerExperience>, a client component that runs the camera/AI.

Components

Organized by feature in src/components/ (trainer, ui, dashboard, exercises, workouts, auth, onboarding). The ui/ folder holds primitives (Button with asChild Slot pattern, Input, Switch, ProgressRing) reused everywhere for consistency.

State management

Deliberately no Redux/Zustand. State is local and layered:

  • React state/refs inside the trainer hook for per-frame data (refs avoid re-rendering 30×/sec — critical for performance).
  • Server is the source of truth for persistent data; pages fetch fresh.
  • localStorage for device-local preferences and dev telemetry (smoothing params, engine override, dev session history).
Why refs, not state, in the loop: updating React state 30–60 times a second would re-render the whole tree and tank FPS. The AI loop writes to useRef values and draws to a canvas directly; only user-visible numbers (rep count, cue) are pushed to state, and the dev HUD is throttled to every 200 ms.

Camera integration

navigator.mediaDevices.getUserMedia() opens the camera into a hidden <video> element. A <canvas> sits on top to draw the skeleton + overlays. Front camera is mirrored (CSS + coordinate flip) so it feels like a mirror; rear camera is not. facingMode toggles front/rear (Chapter 13).

6. AI Pipeline (the big chapter)

This chapter follows a single video frame from the camera all the way to a counted rep and a spoken cue. The whole pipeline runs on the user's device, ~30 times a second, inside the browser. Most of it lives in use-pose-trainer.ts (the loop) and src/lib/pose/ (the math).

Stage-by-stage

  1. Camera: A user gesture starts the stream (required by browsers) and also "unlocks" speech audio. Front camera is mirrored so it feels like a mirror.
  2. Frame capture: We use requestAnimationFrame (rAF) — the browser's "draw a frame now" callback. Each tick we read the current <video> frame. rAF auto-throttles to the display refresh and pauses on hidden tabs (battery friendly).
  3. Pre-processing: The detector internally resizes the frame to its fixed input (e.g. 256×256), scales pixel values, and produces a tensor. We don't hand-code this — the model does it.
  4. Pose detection: The CNN outputs joint positions + confidence. 2D model (MoveNet) → 17 joints; 3D model (BlazePose) → 33 joints with depth. Runs on the GPU via WebGL.
  5. Body-lock: With multi-person output, we select one person (the one near the lock point / largest+centered) and re-identify them each frame so the rep count stays glued to the user.
  6. Landmark filtering: Joints below a confidence threshold are ignored; briefly occluded joints are "held" at their last good spot to avoid a wild jump.
  7. One-Euro smoothing: Each kept joint's x and y are passed through a One-Euro filter to kill jitter without adding lag (Chapter 9).
  8. Angle math: Choose the more visible body side, compute the exercise's defining angle (e.g. hip-knee-ankle for a squat), and normalize it into a 0→1 "progress" value (Chapter 10).
  9. Rep state machine: A turnaround detector counts a rep the instant the user reverses out of a deep-enough bottom — in real time, no pause needed.
  10. Form analysis: Form rules run while descending; a fault must persist several frames and clear a confidence bar before it speaks or rejects a rep.
  11. Voice: Counts and cues are spoken via the Web Speech API with a friendly, simple-English persona; a beep fallback exists.
  12. Draw + telemetry: The skeleton/overlays are drawn to a canvas (also the recording source). In Dev Mode a HUD shows FPS/inference/confidence.
  13. Summary: At set end we compute scores; the rest screen debriefs; the final report saves to the DB.
Why on-device? Streaming video to a server for inference would add 100–300 ms latency (too slow for live coaching), cost a lot of GPU/bandwidth, and create privacy/legal exposure. On-device = instant, cheap, private.

7. Pose Detection & Landmark Map

Which model & why

The default detector is MoveNet MULTIPOSE_LIGHTNING (TensorFlow.js). "MultiPose" = detects several people; "Lightning" = the fast variant. Selectively we switch to BlazePose for 3D (Chapter 8).

Why MoveNetDetail
Real-time on mid-range phones30–60 FPS on WebGL — essential for live coaching
Multi-person + trackingNeeded for body-lock in a busy gym
Runs fully in-browserNo server, private, cheap
Good accuracy/speed trade-offLightning is fast; Thunder is more accurate but slower

How it works internally (plain English)

MoveNet is a convolutional neural network (CNN). Convolutions slide small filters across the image to detect edges → shapes → body parts. The network outputs a heatmap per joint — a grid where the brightest cell is where that joint most likely is. The peak of each heatmap becomes the joint's (x, y), and the peak's strength becomes the confidence score (0–1). Coordinates are normalized to the image, then scaled to canvas pixels.

Confidence scores

Every joint has a score. We use thresholds throughout: <0.25 → occlusion-hold (Chapter 9); <0.3 (MIN_CONF) → joint unusable for rep math; <0.5 (HIGH_CONF) → a detected fault is demoted to a warning rather than rejecting a rep. This prevents the AI from "shouting" about mistakes it isn't sure it saw.

Tracking

MoveNet's tracker assigns IDs across frames so a person stays the "same" person. On top of that we run our own Body-Lock (Chapter 13) for robustness.

8. BlazePose 3D

What it is

BlazePose is Google's pose model (the one behind MediaPipe). In FORGE it runs through TensorFlow.js (tfjs runtime, "lite" variant). It returns 33 landmarks, each with x, y and z (depth) plus visibility — a full 3D skeleton from a single camera.

How it works

Two stages: a fast detector finds the person and a region of interest, then a tracker/regressor predicts all 33 keypoints (and an estimated z) for that region. By tracking the ROI frame-to-frame it avoids re-detecting every frame, which keeps it fast for one person.

The Hybrid pipeline (how 3D actually helps)

This is the key point. When BlazePose is active FORGE runs a Hybrid pipeline: the 2D keypoints still lock/track the athlete and draw the skeleton (fast, robust), while the 3D world landmarks (metres, hip-centred) measure the joint angles used for rep counting — via angle3D() in angles.ts. A 3D angle is depth-invariant: on a bench press, overhead press, row or lat pulldown the working arm travels toward/away from a side/45° camera, which foreshortens a 2D image-plane angle and warps rep detection. Measuring the angle in x/y/z removes that distortion, so reps count reliably from side and angled cameras. If 3D landmarks are momentarily missing, the counter falls back to the 2D angle automatically (see rep-counter.ts → updateRep).

Why only some exercises use it

For a squat or curl from the side, the limb moves across the camera, so a 2D angle is already accurate — 3D would only add cost. The exercises in POSE_3D (bench-press, row, shoulder-press, rdl, pull-down) are exactly the ones where the limb moves in depth, so model-select.ts enables BlazePose only there, and only on capable devices. BlazePose is single-person, so in 3D mode body-lock degrades to signature re-identification (a real trade-off). Production defaults to Auto, which is 2D for most cases and Hybrid for the compound lifts above.

Seeing which pipeline is live

The in-workout HUD shows an AI chip reading 2D / 3D / HYB (Hybrid), and the developer HUD adds model, pipeline and angles (2D image vs 3D world) rows plus an angle3D flag in the exported debug samples — so it's always verifiable which detector and which angle source produced a rep.

Advantages / Limitations / Performance

  • Advantages: depth-invariant joint angles for compound lifts, depth-aware faults, richer 33-point skeleton, stable single-person tracking.
  • Limitations: z is estimated from one camera (not true depth), single-person only, heavier compute.
  • Performance: on weak devices it drops FPS, so a runtime guard (Chapter 17) downgrades 3D→2D if FPS sags below a floor for ~2.5 s. The static device-tier check is the first gate; the FPS fallback is the real guarantee.

9. One-Euro Filter

Raw pose landmarks jitter — even when you hold still, each joint wobbles a few pixels every frame because the model re-estimates from scratch. Jitter makes angles noisy, which causes false reps and flickering form colors. The One-Euro filter (Casiez et al., CHI 2012) removes jitter without the lag a normal smoother adds.

The core idea

It's an adaptive low-pass filter: smooth hard when the joint is nearly still (kills jitter), but smooth lightly when the joint moves fast (stay responsive, no lag). It adapts the cutoff frequency to the measured speed.

Algorithm & formulas

Smoothing factor (exponential filter):
   τ = 1 / (2π · f_c)     α = 1 / (1 + τ/Δt)

1) Estimate speed:   dx = (xₜ − xₜ₋₁) / Δt  → smooth it with α(d_cutoff):   êx
2) Adapt cutoff:   f_c = minCutoff + β · |êx|
3) Smooth value:   x̂ₜ = α(f_c) · xₜ + (1 − α(f_c)) · x̂ₜ₋₁

Because Δt comes from real timestamps, the filter is FPS-independent — it behaves the same at 24 or 60 FPS. This is the exact code in one-euro.ts.

Parameters (tunable in Dev Settings)

ParamDefaultMeaningEffect
minCutoff1.7Baseline smoothing when stillLower = smoother but more lag; higher = snappier but more jitter
beta (β)0.015Speed reactivityHigher = less lag on fast/heavy reps; lower = steadier but can lag
dCutoff1.0Smoothing of the speed estimateRarely changed; lower if it feels twitchy when accelerating

Why it improves rep counting

The rep state machine watches the joint angle reverse direction at the bottom. Jitter creates fake tiny reversals → double counts or phantom reps. One-Euro removes those micro-reversals while preserving the real turnaround, so counts are clean. It also steadies the form colors and ROM/stability scores.

Practical example

Holding the bottom of a squat: raw knee angle might read 98°, 101°, 97°, 100°… One-Euro outputs a steady ~99°, so no false "you came up" trigger. Then you explode upward fast: β raises the cutoff so the filter tracks the quick rise with almost no lag, and the rep registers immediately.

Occlusion hold: the KeypointSmoother also "holds" a joint at its last good position when confidence drops below 0.25 (e.g. a dumbbell briefly hides the wrist), preventing a smoothed-but-wrong jump.

10. Rep Counting Algorithm

Implemented in rep-counter.ts as a bottom-turnaround (extremum) state machine. A rep is counted the instant the user reverses out of a deep-enough bottom — no pause, no full lockout, no return-to-top needed. This was a deliberate redesign after gym testing showed the old method only counted when you stopped moving.

Step 1 — Angle → progress

Each exercise defines a joint triple and three angles (exercises.ts). We compute the live angle and normalize it:

progress = (angle − startAngle) / (activeAngle − startAngle)  → clamped to [0,1]

progress ≈ 0 at the resting/top position, ≈ 1 at the worked/bottom position. Example squat: start 160°, active 100°, ideal 70°.

Step 2 — The state machine

        ┌──────── phase = UP (at top, waiting) ────────┐
        │  track valley (shallowest progress)          │
        │  IF progress > ENTER(0.25) AND               │
        │     progress > valley + TURN(0.1)            │
        │        → user is descending → phase = DOWN   │
        └──────────────────────┬───────────────────────┘
                               ▼
        ┌──────── phase = DOWN (descending/bottom) ────┐
        │  peak = max(peak, progress)  (deepest point) │
        │  sample stability + run form checks          │
        │  IF progress < peak − TURN(0.1)              │
        │        → user reversed → EVALUATE THE REP    │
        └──────────────────────┬───────────────────────┘
                               ▼
              ┌──── peak < MIN_REP_PEAK(0.5)? → ignore (fidget)
              ├──── peak < required depth?      → REJECT "go lower" (invalid++)
              ├──── advanced & sustained error? → REJECT unsafe form (invalid++)
              └──── else → VALID REP++  (score ROM/form/stability/conf)

Step 4 — Mode-adjusted depth

Required depth eases by ±degrees per mode: Beginner gets a +12° easier target, Advanced a −6° stricter one. So beginners aren't punished for slightly shallow reps while advanced lifters are held to standard.

False positives / negatives — honest limits

The engine can't know "ground truth" without video review. Missed reps are proxied by the engine-rejected count; false reps can only be confirmed by watching the recording. The TURN band + min-depth + confidence gates minimize both, but they're a heuristic, not perfection.

Failure sets & counting modes

Two modes: fixed (target reps; the set auto-completes when hit) and failure / reps-to-failure (you press "Finish set" when you can't continue; the AI logs how many real reps you achieved). Both share the same counting core.

11. Form Analysis

Form checks live in form-rules.ts and are evaluated by the rep-counter during the DOWN phase (from CHECK_FROM = 0.35 progress onward). The design goal: never nag about a mistake the AI isn't confident it saw.

The three gates before a fault "counts"

  1. View gate: a check only runs if the camera view matches what it needs (e.g. a "back rounding" check needs a side view). viewMatches(check.view, orientation).
  2. Confidence gate: if the involved joints are below HIGH_CONF (0.5), an "error" is demoted to a warning — visible but it won't reject a rep.
  3. Persistence gate: a status must hold for SUSTAIN = 6 consecutive frames (run-length tracking) before it's "active". One noisy frame never triggers a cue.

How a rep is judged Good / Bad / Incomplete

VerdictCondition
PerfectROM ≥ 90 AND form ≥ 85 AND stability ≥ 80

Scoring formulas

form = max(0, 100 − errors×30 − warns×12)
rom = clamp(peak / idealProgress) × 100   (idealProgress from idealAngle)
stability = clamp(1 − (hipSwayRange / torsoLength) × 1.2) × 100
confidence = mean(per-frame min joint score) × 100

Honest limit: true back-rounding and heel-lift need depth or a clean side view. In 2D from a bad angle these are reported conservatively (warning, not rejection) to avoid false alarms.

14. Computer Vision Foundations

This chapter explains the CV concepts the app relies on — useful for "explain the fundamentals" questions.

Landmarks & coordinates

A landmark (keypoint) is a body joint the model locates: {x, y, score, name} (plus z in 3D). Coordinates are first normalized (0–1 of the image) then scaled to canvas pixels. Image y grows downward (top-left origin) — important when comparing "above/below" (e.g. wrist above shoulder means smaller y).

Vectors & joint angles

To measure a joint angle at B between A and C, form two vectors BA and BC and use the dot product:

BA = A − B,  BC = C − B
cos θ = (BA · BC) / (|BA| · |BC|)  →   θ = arccos(cos θ) × 180/π

This is exactly angle(a,b,c) in angles.ts (clamped to avoid NaN). angleFromVertical uses atan2(dx, dy) to measure a segment's tilt vs vertical (for torso lean / body-line checks). The 3D variant angle3D(a,b,c) uses the same dot-product formula over x/y/z from BlazePose world landmarks, giving a depth-invariant joint angle for the Hybrid pipeline (Chapter 8).

Distance calculations

Euclidean distance hypot(dx, dy) measures limb/segment lengths — used for vector magnitudes, torso length (stability normalization), and framing checks.

Temporal smoothing & motion tracking

Per-joint One-Euro filtering over time (Chapter 9) plus a light EMA on the rep angle. Motion is tracked as the change in the normalized "progress" signal; its direction (increasing/decreasing) drives the rep phase.

Depth estimation

2D has no depth. BlazePose 3D estimates z from a single camera via a model trained on 3D-labeled data — an inference, not a measurement, so it's approximate. Used only for depth-sensitive faults (Chapter 8).

Best-side selection & orientation

bestSide averages confidence over each body side and uses whichever is more reliably seen (so a side-on user is tracked on the camera-facing side). detectOrientation classifies the camera view (front vs side) from the relative positions of shoulders/hips, letting form checks adapt.

17. Performance Optimization

Live coaching means everything per frame must finish in ~16–33 ms. Optimizations span the whole stack.

FPS & adaptive model selection

  • Static device-tier (device-tier.ts): low/mid/high gates whether 3D is even attempted.
  • Runtime FPS guard (in use-pose-trainer.ts): an FPS EMA; if FPS sits below a floor (24 mid / 18 low) for ~2.5 s, it downgrades 3D→2D automatically (Auto mode only) and logs a fallback event.
  • This two-layer approach guarantees responsiveness even when the static guess is wrong.

CPU / GPU

  • TF.js WebGL backend runs inference on the GPU; the CPU handles only light geometry.
  • Model loaded once and reused (modelRef); no reload per set.
  • Skeleton drawn on canvas (GPU compositing) instead of DOM nodes.

Memory

  • Tensors are short-lived per frame; the detector manages disposal.
  • Debug log capped at 8000 events; dev session history capped at 200.
  • Refs instead of state arrays for per-frame data → no React garbage from re-renders.

Latency reduction

  • On-device inference (no network round-trip).
  • One-Euro tuned for low lag (β raises responsiveness on fast reps).
  • Reps counted on turnaround (instant), not on lockout.

Frame handling & battery

  • requestAnimationFrame auto-throttles to the display and pauses on hidden tabs (saves battery).
  • HUD/telemetry updates throttled to 200 ms; voice cues throttled (≥1.5 s gaps) to avoid spam and audio overlap.
  • Lighter "Lightning" model + "lite" BlazePose variant chosen for mobile battery/thermals.

Render performance

  • Per-frame numbers kept in refs; only user-visible values trigger React updates.
  • Heavy TF.js trainer dynamically imported so other pages stay light.
  • Service-worker cleanup avoids stale, slow cached bundles.

19. Security & Privacy

Camera permissions & privacy

  • The camera only opens after an explicit user gesture (browser-enforced), and the browser shows its own in-use indicator.
  • Video never leaves the device for inference — pose detection runs locally. Recordings are saved locally (download / Web Share); we don't upload media.
  • This is the strongest privacy story possible for a camera app: the sensitive data (your body on video) stays on your hardware.

Authentication & session security

  • Passwords hashed with bcrypt (salted, slow) — never stored in plaintext.
  • Auth token is a signed JWT in an HTTP-only, Secure, SameSite cookie — unreadable by JS (XSS-resistant) and not sent cross-site (CSRF-resistant).
  • Google sign-in tokens are verified server-side before we trust them.
  • Mandatory login: src/proxy.ts blocks all app/trainer routes for unauthenticated users.

Data protection

  • Input validated with zod on every API route (rejects malformed/malicious payloads).
  • Prisma uses parameterized queries → SQL-injection safe.
  • Secrets (DB URL, JWT secret, OAuth IDs) are environment variables, never committed; .env is gitignored.
  • Only structured workout data is stored server-side — minimal personal data footprint.

Local storage scope

localStorage holds only non-sensitive device preferences and dev-only telemetry. No passwords or tokens are kept there.

Operational note: real database credentials were shared in chat during setup — those should be rotated. Always treat any secret that touches a chat/log as compromised.

Future cloud architecture (when added)

  • If recordings ever sync to the cloud: encrypt at rest + in transit, signed time-limited upload URLs, per-user storage isolation, explicit opt-in consent.
  • Rate-limiting + audit logging on APIs; secret manager instead of plain env vars at scale.

21. 100 Interview Questions & Answers

Grouped beginner → intermediate → advanced. Each: answer, why it's right, and the common mistake.

Beginner (1–30)

  1. What is FORGE / AI-Trainer?
    A web app that uses your camera + on-device AI to detect your body, count reps, score form, and coach you by voice in real time. Why right: it captures the three pillars (detect, count, coach). Mistake: calling it "just a workout logger" — the AI vision is the core.

    Affordable, always-available form correction + automatic tracking without a human trainer. Mistake: focusing only on counting and forgetting the injury-prevention/form angle.

  4. Why run the AI in the browser, not the server?

Intermediate (31–65)

  1. Explain the rep state machine.
    Two phases (UP/DOWN). UP→DOWN when progress exceeds ENTER and rises past the valley+TURN; in DOWN we track the peak; when progress drops below peak−TURN the rep is evaluated. Mistake: describing it as a simple threshold cross (that double-counts on jitter).
  2. Why count on turnaround instead of lockout?
    Gym testing showed lockout-based counting only fired when the user paused; turnaround counts mid-motion and handles heavy grind reps. Mistake: not citing the real-world failure that motivated it.
  3. How do you prevent jitter double-counts?
    One-Euro smoothing + a TURN reversal band + MIN_REP_PEAK depth gate. Mistake: relying on smoothing alone.
  4. Give the One-Euro formula.
    α = 1/(1 + τ/Δt), τ = 1/(2π f_c); estimate speed êx, set f_c = minCutoff + β·|êx|, then x̂ = α·x + (1−α)·x̂_prev. Mistake: forgetting the cutoff adapts to speed.
  5. Why is One-Euro FPS-independent?
    It uses real Δt timestamps, so behavior is the same at 24 or 60 FPS. Mistake: assuming a fixed per-frame coefficient.
  6. What are minCutoff and beta?
    minCutoff = baseline smoothing when still; beta = how much smoothing relaxes with speed. Mistake: swapping their roles.
  7. How is a joint angle computed?
    Dot product of the two vectors from the middle joint: θ = arccos((BA·BC)/(|BA||BC|)). Mistake: forgetting to clamp cos to [−1,1] (NaN risk).
  8. How is range of motion (ROM) scored?
    peak progress ÷ idealProgress, clamped, ×100. Mistake: using the required (mode) depth instead of the ideal angle.
  9. How is stability scored?
    1 − (hip-sway range ÷ torso length) × 1.2, clamped, ×100. Mistake: measuring absolute pixels without normalizing by torso (breaks across distances).
  10. How is form scored?
    100 − errors×30 − warns×12, floored at 0. Mistake: treating warnings and errors the same.
  11. How do you avoid false form alarms?
    Three gates: view match, confidence ≥ HIGH_CONF, and persistence for SUSTAIN (6) frames. Mistake: firing a cue on a single bad frame.
  12. What is the confidence gate's effect on faults?
    A low-confidence "error" is demoted to a "warning" so it won't reject a rep. Mistake: letting an unsure model reject valid reps.
  13. How does the overhead-press false-rep fix work?
    requireWristAboveShoulder: a straight elbow only counts as worked if the wrist is above the shoulder, so arms-at-sides isn't a rep. Mistake: relying on elbow angle alone.
  14. How does mode change required depth?
    An ease term (±degrees) shifts the active angle before converting to required progress. Mistake: hard-coding one depth for everyone.
  15. How do you pick which body side to measure?
    bestSide averages joint confidence per side and uses the more visible one. Mistake: always using the left side.
  16. What is orientation detection for?
    To know if the camera sees front or side, so form checks only run when valid. Mistake: running side-only checks on a front view.
  17. Why refs instead of state in the loop?
    Updating React state 30×/sec re-renders the tree and tanks FPS; refs avoid that. Mistake: putting the rep count in state and writing it every frame.
  18. How is the HUD kept cheap?
    Telemetry is throttled to every 200 ms and only shown in dev. Mistake: updating the HUD every frame.
  19. What is the hybrid 2D/3D pipeline?
    model-select.ts picks BlazePose only for depth-sensitive compound lifts (bench-press, row, shoulder-press, rdl, pull-down) on capable devices; otherwise MoveNet 2D. In BlazePose mode it runs Hybrid: 2D keypoints track/lock the athlete while 3D world landmarks measure the joint angles (angle3D) for depth-invariant rep counting. The HUD's AI chip shows 2D / 3D / HYB. Mistake: saying 3D just adds a fault check — it now drives the rep-angle measurement; or using 3D everywhere (slower, single-person).
  20. How does device-tier fallback work?
    Static tier gates 3D; a runtime FPS EMA downgrades 3D→2D if FPS stays below a floor ~2.5 s (Auto only). Mistake: trusting the static check alone.
  21. Why does 3D mode weaken body-lock?
    BlazePose is single-person, so multi-person re-identification isn't available. Mistake: claiming 3D is strictly better.
  22. How are reps validated vs rejected?
    Reject if depth < required (incomplete) or, in advanced, a sustained high-confidence error; else valid. Mistake: rejecting on any momentary fault.
  23. What's the occlusion-hold mechanism?
    If a joint's score < 0.25, the smoother returns its last good position instead of a noisy jump. Mistake: letting an occluded joint snap to a wrong location.
  24. How is the workout recorded?
    canvas.captureStream() → MediaRecorder, capturing the skeleton overlay too. Mistake: recording the raw video element without overlays.
  25. Why can't the voice be in the recording?
    Web speechSynthesis output isn't routed to a capturable media stream. Mistake: promising in-video voice on the web (needs native).
  26. How is input validated on the API?
    zod schemas parse every request body; invalid input is rejected before the DB. Mistake: trusting client data.
  27. How are SQL injections prevented?
    Prisma uses parameterized queries; we never build raw SQL strings. Mistake: concatenating user input into queries.
  28. How does Google OAuth work here?
    The Google ID token is verified server-side, then we mint our own JWT. Mistake: trusting the client-sent token without verification.
  29. What does src/proxy.ts do?
    Acts as Next 16 middleware: checks the JWT cookie and redirects unauthenticated users — enforcing mandatory login. Mistake: protecting only some pages.
  30. How is failure-set (reps-to-failure) handled?
    Same counting core; the user presses "Finish set" and we log the real reps achieved. Mistake: needing a preset target.
  31. How do you handle too-fast (momentum) reps?
    If <450 ms since the last rep, cue "slow down, control it". Mistake: still scoring them as perfect.
  32. What's stored per workout session?
    Per-set reps, weight, ROM/form/stability/confidence scores, volume — for analytics and PRs. Mistake: storing only total reps.

Advanced (66–100)

  1. Walk through the full per-frame pipeline.
    rAF tick → read video frame → model inference (GPU) → body-lock select person → confidence filter + occlusion hold → One-Euro smoothing → bestSide + joint angle → progress → rep state machine → form checks → voice → canvas draw → (dev) telemetry. Mistake: omitting body-lock or putting smoothing after the angle.
  2. Why a heuristic state machine instead of an ML rep classifier?
    It's interpretable, needs no training data, runs in O(1)/frame, and is tunable per exercise; an ML counter needs labeled data and adds latency. Mistake: assuming ML is automatically better.
  3. How would you reduce false reps further without 3D?
    Tighten TURN/MIN_REP_PEAK, add velocity-based rep validation, require minimum rep duration, and cross-check a secondary joint. Mistake: only increasing smoothing (adds lag, hides real turnarounds).
  4. Why is z in BlazePose only "estimated"?
    It's regressed from a single 2D image by a model trained on 3D data — an inference, not a measured depth (no stereo/ToF). Mistake: treating z as metric-accurate.
  5. Trade-offs of MoveNet Lightning vs Thunder?
    Lightning: faster, multi-person, slightly less accurate. Thunder: more accurate, slower, single-pose. We need speed + multi-person for body-lock, so Lightning. Mistake: picking accuracy without weighing FPS/lock.
  6. How does the FPS guard avoid oscillation (flapping)?
    It downgrades only after FPS stays below the floor for a sustained ~2.5 s window (EMA), and doesn't auto-upgrade mid-session. Mistake: switching engines on a single slow frame.
  7. What's the complexity of the whole per-frame pipeline?
    Dominated by the CNN inference (fixed cost for a fixed input); the rest is O(n) over ~17–33 landmarks, effectively constant. Mistake: claiming it scales with video resolution linearly in our code (the model fixes input size).
  8. How do you keep memory stable over a long session?
    Per-frame tensors are disposed by the detector, per-frame data lives in refs (no React garbage), and logs/history are capped (8000 / 200). Mistake: accumulating per-frame arrays in state.
  9. How would you add real exercise auto-classification later?

24. Final Summary

Key takeaways

  • FORGE is a client-heavy, on-device AI fitness coach: the browser does pose detection, rep counting, form analysis, and voice; the server only stores structured data.
  • That single choice drives everything good about it: low latency, low cost, strong privacy.
  • The AI is built from interpretable, tunable algorithms (state machine + geometry + One-Euro), not a black box — which makes it debuggable and reliable.
  • Robustness comes from layered defenses: confidence gates, persistence gates, body-lock, occlusion-hold, and a runtime FPS fallback.
